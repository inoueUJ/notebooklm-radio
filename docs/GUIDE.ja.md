## 1. できること・できないこと

**できること**

- RSS / Atom / sitemap のフィードを 1 日 2 回(時刻は自分で決める)見に行き、新しい記事だけを Google NotebookLM のノートブックに入れて、音声概要(二人の対談形式のラジオ)の生成を始める。
- ノートブックは「1 日 × 1 トピック」で分かれる。AI ニュースの番組と、クラウドの変更点の番組は別々にできる。トピックごとに会話の形式・長さ・指示文を変えられる。
- Slack か Discord に、今日の記事一覧と各ノートブックへのリンクが届く。
- 古いノートブックは 7 日で自動削除(最初は「消す予定」を通知するだけの dry-run)。
- サーバーもデータベースも無い。GitHub Actions の cron だけで動く。

**できないこと・注意**

- NotebookLM に公式 API は無く、非公式の CLI(notebooklm-py)であなた自身の Google セッションを使う。Google 側の変更で止まる可能性があり、約 3.5 週ごとに手元で再ログインが要る([8 章](#8-運用-35-週ごとの更新と掃除))。
- 音声の生成には 1 日の上限がある(無料 3 本、Google AI Plus 6 本、Pro 20 本)。「ノートブック数 × 1 日の実行回数」がその日の本数になる。
- 生成された音声は個人利用の範囲で。元記事の著作権と NotebookLM の規約があるので、公開配信は想定していない。
- ボット対策で記事本文を取れないサイト(openai.com 等)は、フィードの要約文だけを入れる。ラジオもそう断って話す。

## 3. 設定を作る(ビルダー)

設定ファイルは `config.yaml` の 1 枚だけです。手で書けますが、**[設定ビルダー](https://inoueuj.github.io/tech-feed-catalog/)** で作ると、後で困ることを先に教えてくれます。ブラウザだけで完結し、何も送信しません(カタログに無いフィードの疎通確認だけ、そのサイトの Worker が代わりに取りに行きます)。日本語と英語は右上で切り替えられます。

開くと「かんたん」モードで、4 段階の案内が出ます。

**1. 何を追う?** 技術名のチップ(Claude、Rust、Next.js、Cloudflare、日本語テックブログ …)を押すと、対応するフィードが入ります。押すたびに右上の件数が増えます。カタログに無いものは同じ画面の下から足せます。Zenn のトピック、Zenn のユーザー、Qiita のタグ、任意のフィード URL。**確認**を押すと、本当にフィードか、何件返すか、日時が付いているか、月に何件くらい出るかが分かります。

**2. 番組に分ける** 選んだフィードは番組(= NotebookLM のノートブック = 1 日 1 本のラジオ)ごとの箱に入ります。目安は「混ぜて聴いて違和感がないか」。AI モデルの発表と Cloudflare の changelog を同じ番組にすると散らかります。箱の名前は自由に変えられ、プルダウンで別の箱へ移せます。箱ごとに雰囲気を「じっくり」(対談形式で深掘り)か「手短に」から選び、「細かく」で会話の形式・長さ・指示文を直接指定できます。流量が多いフィード(はてな、Hacker News、Zenn トレンド)には **最新だけ** が自動で付きます。「毎回最新 N 件だけ拾って、残りは読んだことにする」設定で、付けないと 1 週間前の記事を永遠に流し続けます。

**3. いつ聴く?** 音声の言語、タイムゾーン、朝の時刻と 2 回目の有無、NotebookLM のプラン。プランを選ぶと「番組数 × 実行回数 = 1 日の本数」が表示され、上限を超えると赤くなります。超える場合は番組を減らすか、2 回目を切ってください。「あなたのスタック」に書いたものは指示文の雛形に入ります。

**4. できあがり** `config.yaml` の全文と、実行時刻を UTC に変換した cron の 2 行が出ます(GitHub の cron は UTC でしか書けません)。**ダウンロード**で保存し、cron の 2 行はコピーしてください。**共有リンク**を押すと、この構成を丸ごと復元できる URL がコピーされます。ブラウザを閉じても、同じブラウザなら状態は残ります。

「知っておくこと」の欄に出るもの: 取得に失敗しているフィード、ボットを拒否するホスト、同じ記事を配信する 2 つのフィード(両方入れると全記事が 2 回入る)、要約しか取れないフィード、処理が追いつかない流量。

右上の「一覧で選ぶ」に切り替えると、カタログ 76 件をカテゴリや流量で絞りながらチェックする従来の画面になります。選んだ内容は両モードで共通です。OPML やフィード URL の一覧が欲しいだけの人はこちらを使ってください。

## 4. リポジトリを作って設定を入れる

1. https://github.com/inoueUJ/notebooklm-radio を開き、**Use this template → Create a new repository**。名前は自由、**Private** を選びます(bot があなたの購読履歴を `state.json` としてコミットし続けるため)。
2. clone します: `gh repo clone あなたの名前/リポジトリ名`
3. `config.yaml` を、ビルダーでダウンロードしたファイルで**丸ごと置き換え**ます。既存の `feeds:` の下に貼り足すのではありません。
4. `.github/workflows/rss-radio.yml` を開き、`schedule:` の下の `- cron:` 2 行を、ビルダーの `cron` タブの 2 行に差し替えます。
5. 検査します。何も実行せず、設定ファイルを読んで問題を列挙するだけです:

```bash
python radio_batch.py --check-config
```

`config.yaml OK: 8 feed(s), topics: AI, Dev, Infra` のように出れば通っています。この検査は CI でも毎回 batch の前に走るので、typo で黙って壊れることはありません。手元に `yaml` などのパッケージが無くて動かない場合は、`pip install -r requirements.txt` で入るか、CI に任せても構いません。

6. コミットして push します。まだ何も動きません(secret が無いので、動いても止まります)。

## 5. セットアップウィザードを走らせる

clone の中で:

```bash
python scripts/setup.py
```

やることを順に表示しながら進みます。

1. **doctor** — Python、リポジトリ、uv、gh のログイン、notebooklm CLI、認証ファイルの有無と古さ、secret の有無、config.yaml の検査。足りないものには直し方が出ます。
2. **notebooklm CLI を入れる** — CI が使うのと同じバージョンを uv で入れます。
3. **Google にログイン** — `notebooklm -p ci login` が走り、ブラウザが開きます。NotebookLM を使う Google アカウントでログインしてください。`ci` という専用プロファイルに保存されます。普段使いと分けるのは、混ぜると認証の寿命が 3 日に縮むからです([OPERATIONS.md](OPERATIONS.md))。
4. **secret を登録** — 認証ファイルを `NOTEBOOKLM_AUTH_JSON` として登録します。ファイルの中身は画面にもシェルの履歴にも出ません。あわせて登録日をリポジトリ変数に記録します。
5. **webhook を登録** — URL を聞かれます(入力は表示されません)。空で Enter すると飛ばせますが、通知が一切来なくなります。
6. **初回実行** — その場でワークフローを起動するか聞かれます。

webhook URL の取り方:
- **Slack**: https://api.slack.com/apps → Create New App → From scratch → 左メニュー Incoming Webhooks → On → Add New Webhook to Workspace → チャンネルを選ぶ → 出てきた `https://hooks.slack.com/services/...` をコピー。
- **Discord**: 通知したいチャンネルの設定 → 連携サービス → ウェブフック → 新しいウェブフック → ウェブフック URL をコピー。

`python scripts/setup.py doctor` はいつでも実行でき、何も変えません。`python scripts/setup.py renew` は 3.5 週ごとの更新用です([8 章](#8-運用-35-週ごとの更新と掃除))。

うまくいかないとき:
- 「workflows are disabled」のような失敗 → テンプレートから作った直後は Actions が無効なことがあります。リポジトリの Actions タブで有効化して、もう一度ウィザードか `gh workflow run rss-radio.yml` を。
- `gh` が「not logged in」 → `gh auth login` してから再実行。
- `notebooklm` が見つからない → 新しいターミナルを開く(PATH に `~/.local/bin` が加わるのはインストール後)。
- Windows(PowerShell)でも同じ手順で動きます。ウィザードはリダイレクト(`<`)を使いません。

## 6. 毎朝の使い方

実行のたびに Slack(Discord)にこう届きます。

```
🎙️ Anthropic、Cloudflare が新しい記事出してたよ（5件）
ラジオの生成を開始したよ〜
《AI》 <Tech Radio AI 2026-09-26>
・<記事タイトル>（Anthropic）
・<記事タイトル>（OpenAI・要約のみ）
《Infra》 <Tech Radio Infra 2026-09-26>
・<記事タイトル>（Cloudflare）
```

- 見出しのリンクを押すと、そのノートブックが NotebookLM で開きます。アプリで探す必要はありません。
- 「生成を開始した」であって「できた」ではありません。音声は NotebookLM 側で 10〜20 分かけて作られます。NotebookLM アプリの通知を有効にしておくと、完了が分かります。
- `要約のみ` は、ボット対策で本文を取れず、フィードの要約文だけを入れた記事です。ラジオもその前提で話します。
- 見出しに `（音声は未生成）` と付いていたら、記事は入ったが音声を始められなかったということ。理由は別の通知に出ます(多くは 1 日の上限)。アプリから手で「音声概要を生成」できます。
- 新着が無い回は `😪 今回は新着なしだったよ` が来ます。**何も来ないのは異常**です([9 章](#9-困ったとき))。
- 2 回目の実行では、その回に新しく入った記事だけで別の音声が作られます。朝の記事は再放送されません。
- 初回だけは特別で、各フィードの最新 1 件だけを処理し、過去分は読んだことにします。過去記事の洪水は起きません。

1 週間ほど経つと `🧹 [ドライラン] 7日より古いラジオ 2件を削除する予定` のような通知が来ます。挙げられたノートブックが本当に古いラジオだけなら、`config.yaml` の `cleanup.dry_run` を `false` にしてください。それ以降は本当に削除されます。削除対象は「このバッチが作った命名に完全一致するノートブック」だけで、手で作ったノートブックには触りません。

## 7. 設定を変える

すべて `config.yaml` です。変えたらコミットして push するだけで、次の実行から反映されます。push しても即実行はされません(手で回すなら `gh workflow run rss-radio.yml`)。

| やりたいこと | どこを変えるか |
|---|---|
| フィードを足す・外す | `feeds:` に項目を足す/消す。迷ったらビルダーで作り直して丸ごと置き換える(ビルダーの Share link を残しておくと楽) |
| フィードを別の番組へ | そのフィードの `topic:` を変える |
| 番組の形式・長さ・指示文 | `topics:` の下のその番組の `audio:` に `format` / `length` / `prompt` |
| 全番組共通の指示文 | `settings.audio.prompt` |
| 実行時刻 | `.github/workflows/rss-radio.yml` の `- cron:` 2 行(UTC)。ビルダーの `cron` タブが変換してくれる |
| 1 回に処理する記事数 | `settings.limits.per_feed`(フィードごと、既定 3)と `total`(全体、既定 15)。超えた分は捨てずに次回へ |
| 流量の多いフィード | そのフィードに `mode: latest`(最新 N 件だけ拾い、残りは読んだことにする) |
| 音声の言語 | `settings.language`(ja / en など) |
| 何日でノートブックを消すか | `settings.cleanup.retention_days` |
| 記事ページがボット対策で取れないサイト | そのフィードに `source_mode: text` |

変えたあとは `python radio_batch.py --check-config` で検査できます。使えるキーは [`config.schema.json`](../config.schema.json) に全部書いてあります。知らないキーを書くとエラーになります(typo が黙って既定値に落ちるより安全です)。

新しく足したフィードは、初回は最新 1 件だけ処理されます。

## 8. 運用: 3.5 週ごとの更新と掃除

**認証の更新(約 3.5 週ごと)**
Google のセッションは手元では生き続けますが、secret に凍結したコピーは約 3.5 週で切れます。切れると `Tech Radio 実行エラー発生` の通知に `Authentication expired` と復旧手順が出ます。やることは 1 つ:

```bash
python scripts/setup.py renew
```

ブラウザでログインし直し、secret を入れ替え、その場で再実行するか聞きます。2 分ほどです。`python scripts/setup.py doctor` で認証の古さがいつでも見られます(21 日を超えると警告)。

守ること:
- 手元で普段 `notebooklm` を使うときは、`-p ci` を付けない(普段用の `default` プロファイルを使う)。CI 用と混ぜると寿命が 3 日に縮みます。
- `state.json` は bot のものです。手で編集もコミットもしないでください。消すと全フィードが初回扱いに戻ります(最後の手段)。

**掃除**
`cleanup.dry_run: false` にしてあれば、`retention_days` より古いラジオは朝の回で自動削除され、`🧹 7日より古いラジオ 2件を削除したよ` と通知されます。

**月次の健康診断**
毎月 1 日に、30 日以上新着のないフィードが `🩺` 付きで通知されます。配信停止やサイト構造の変化の兆候です。

**GitHub Actions の無料枠**
1 回 1〜4 分なので、1 日 2 回でも private リポジトリの無料枠(月 2000 分)に収まります。

## 9. 困ったとき

| 見えたもの | 意味 | やること |
|---|---|---|
| 何も届かない日が続く | 通知の仕組みごと止まっている | リポジトリの Actions タブで最後の実行を見る。secret の `NOTIFY_WEBHOOK_URL` が入っているか `doctor` で確認 |
| `🚨 テスト/lint が失敗したので、今回の batch は実行されていない` | コード側の検査で止まった。ラジオは作られない | リンク先の実行ログを見る。`config.yaml` の検査で止まった場合はその内容が出る |
| `Tech Radio 実行エラー発生` + `Authentication expired` | 認証切れ | `python scripts/setup.py renew` |
| `Tech Radio 実行エラー発生` + `ConfigError` | 設定ファイルの誤り | 通知に列挙された箇所を直す。`--check-config` で確認 |
| 見出しに `（音声は未生成）` + 別通知に `rate_limited` | その日の音声上限に当たった | ノートブックを減らす、2 回目の実行を切る、プランを上げる。記事はノートブックに入っているので、アプリから手動生成もできる |
| `⚠️ RSSフィードの取得に問題があるよ ・X: HTTP 403` | そのフィードが取れない。既読状態は触っていない | 一時的なら放置。続くならフィード URL を見直す。403 が続くならボット拒否 |
| `⚠️ 以下はサイトのボット対策で本文を取り込めなかった` | 記事ページがボット対策ページだった | そのフィードに `source_mode: text` を付ける |
| `😪 今回は新着なし` が毎回 | 本当に新着が無いか、`feeds:` が空 | `--check-config` の出力にフィード数が出る |
| 同じ記事が 2 つ入る | 同じ記事を配信する 2 フィードを両方購読している(例: Vercel の blog と atom) | 片方を外す。ビルダーは選んだ時点で警告する |
| 古い記事ばかり流れる | 流量がフィードごとの上限を超えていて、古い順に消化している | そのフィードに `mode: latest`、または `limits.per_feed` を上げる |
| 音声がノートブックに現れない | 生成は始まったが失敗した(NotebookLM 側) | アプリから再生成。繰り返すなら上限や記事の内容を疑う |
| 夕方の回が翌日のノートブックに入った | GitHub の実行が数時間遅れて日付をまたいだ | cron を早める。遅延は GitHub 側の事情で、:00 と :30 は特に混む |

## 10. まず試してみたい人へ

本番のリポジトリを汚さずに一通り体験したいときの手順です。作者自身の確認手順でもあります。

1. ビルダーでフィードを 2〜3 件だけ選び、ノートブックは 1 つ、2 回目の実行は切っておきます(音声上限を食わないため)。
2. テンプレートから `radio-trial` のような名前で Private リポジトリを作り、設定を入れます([4 章](#4-リポジトリを作って設定を入れる))。
3. ウィザードは、本番と別のログインプロファイルで動かします。本番の `ci` を触らずに済みます:

```bash
python scripts/setup.py --profile trial --no-run
gh workflow run rss-radio.yml
```

4. Actions タブで実行を眺め、Slack にリンク付きの一覧が来て、NotebookLM にノートブックができ、20 分後に音声ができるところまで見ます。
5. 終わったら、リポジトリを消すか、Actions タブでワークフローを無効化します。放っておくと毎日 2 回動き、同じ Google アカウントの音声上限を使い続けます。

このお試しで分かること: セットアップにどれくらい手間がかかるか、通知の読み方、ノートブックの見つけ方。分からないこと: 3.5 週後の認証切れの体験(待つしかありません。`doctor` の警告で先に分かります)。

## 11. 用語

- **フィード**: サイトが配っている「新着一覧」。RSS / Atom が普通の形式で、無いサイトは sitemap.xml で代用する。
- **config.yaml**: 設定ファイル。フィード、番組(トピック)、音声の設定、掃除の設定がすべて入っている。
- **state.json**: 「どこまで読んだか」の記録。bot が毎回コミットする。
- **トピック / ノートブック**: フィードのまとまり = 番組。1 日 × 1 トピックで NotebookLM に 1 冊でき、1 冊につき 1 本の音声ができる。
- **音声概要**: NotebookLM が生成する対談形式のラジオ。1 日の本数に上限がある。
- **cron**: GitHub Actions に「この時刻に実行」と予約する行。UTC で書く。
- **secret**: GitHub Actions だけが読める秘密の値。認証(`NOTEBOOKLM_AUTH_JSON`)と通知先(`NOTIFY_WEBHOOK_URL`)の 2 つ。
- **webhook**: Slack や Discord に外から投稿するための URL。
- **プロファイル(`ci` / `default`)**: notebooklm CLI のログイン保存先。CI 用と普段用を分ける。
- **ビルダー**: config.yaml と cron 行を作る Web ページ。https://inoueuj.github.io/tech-feed-catalog/
- **newest only / `mode: latest`**: 流量の多いフィードで、最新 N 件だけ拾って残りを読んだことにする設定。
